# التصميم الهندسي والأمان — قرارات تأسيسية

## قبل اختيار التقنية
افحص المستودع الموجود فعليًا. المخطط قد يقترح تقنيات معينة، لكن لا تغيّر التقنية أو تضف خدمات مدفوعة قبل مقارنة الواقع بالمخطط وتوثيق القرار.

## حدود النظام
- واجهة المستخدم.
- واجهات التطبيق الخلفية والخدمات.
- قاعدة البيانات وملفات المرفقات.
- نظام الهوية والصلاحيات.
- معالجة المهام الخلفية والأحداث.
- تكاملات خارجية: واتساب، الدفع، الذكاء الاصطناعي، ومصدر بيانات الأدوية.
- المراقبة وسجلات التدقيق والنسخ الاحتياطي.

## العزل متعدد العملاء
- يجب أن يكون `tenant_id` أو ما يعادله جزءًا من نموذج البيانات حيث يلزم.
- يجب فرض العزل في طبقة قاعدة البيانات/السياسات، وليس إخفاء البيانات في الواجهة فقط.
- اختبر محاولات القراءة والتعديل بين عيادتين، بما في ذلك الملفات والتقارير والمهام الخلفية وروابط التنزيل.
- لا تسمح للمهام المجدولة أو webhooks بالعمل دون التحقق من سياق العميل.
- لا تعتمد على معرفات غير قابلة للتخمين كبديل للصلاحيات.

## الهوية والصلاحيات
- مصفوفة صلاحيات موثقة لكل دور ولكل عملية.
- جلسات آمنة، وإجراءات استعادة الحساب، وتحديد معدل المحاولات.
- مصادقة متعددة العوامل للأدوار الحساسة حيثما أمكن.
- فصل صلاحيات دعم المنصة عن صلاحيات العيادة، وتسجيل أي وصول دعم إلى بيانات العملاء.
- لا تُظهر بيانات مرضى لموظفي المنصة إلا عند وجود ضرورة وصلاحية موثقة.

## البيانات والأمان
- TLS للاتصال، وتشفير مناسب للبيانات المخزنة والنسخ الاحتياطية.
- إدارة الأسرار خارج الكود وسجلات التشغيل.
- تحقق من المدخلات، وحماية من CSRF/XSS/SQL injection بحسب التقنية المستخدمة.
- رفع الملفات مع فحص النوع والحجم، وتخزين خاص، وروابط تنزيل قصيرة العمر.
- سجلات التدقيق تسجل الفاعل والوقت والعملية والكيان والنتيجة دون تسجيل أسرار أو تفاصيل طبية غير لازمة.
- سياسة احتفاظ وحذف تشمل قواعد البيانات والملفات والسجلات والنسخ الاحتياطية.
- خطة استجابة للحوادث تشمل الاكتشاف والاحتواء والتوثيق والإخطار وفق الالتزامات المنطبقة.

## النسخ الاحتياطي والتعافي
- نسخة منفصلة عن الخادم الأساسي.
- تشفير النسخ وتقييد صلاحياتها.
- تحديد أهداف الاستعادة RPO/RTO مع صاحب المشروع قبل الإنتاج.
- اختبارات استعادة دورية موثقة؛ نجاح إنشاء نسخة لا يثبت إمكانية استعادتها.
- خطة موثقة لانقطاع مزود الاستضافة أو فقدان الوصول.

## التكاملات
- لكل webhook توقيع/تحقق، ومعالجة تكرار، وسجل فشل، وإعادة محاولة بحدود.
- لا تخزن أسرارًا في قاعدة البيانات كنص مكشوف.
- لا تفعّل واتساب أو الدفع أو خدمات AI على الإنتاج قبل اختبار sandbox وموافقة صاحب المشروع.
- لا ترسل بيانات طبية إلى مزود AI خارجي قبل تقييم موقع المعالجة، وشروط الاستخدام، والاحتفاظ، والتدريب، والعقد.

## قرار الاستضافة
الاستضافة داخل مصر خيار مبدئي محافظ للمشروع، وليست إثبات امتثال تلقائيًا. يجب التحقق من موقع البيانات الفعلي، وموقع النسخ الاحتياطية والسجلات والدعم، والعقود والتراخيص والالتزامات القانونية مع مختص قبل بيانات الإنتاج.

## قرار قاعدة الأدوية
لا تُنسخ قاعدة الهيئة أو أي مصدر آخر للاستخدام التجاري قبل موافقة أو ترخيص مكتوب يحدد الوصول الآلي والتخزين والعرض والتحديث. افصل بيانات تعريف الدواء عن توصيات الجرعات والتداخلات التي تحتاج مصادر موثوقة ومراجعة طبية.


## البنية الهجينة للذكاء الاصطناعي والأتمتة
- **Backend:** المصدر الوحيد المعتمد للهوية والصلاحيات وقواعد العمل والبيانات الطبية والمالية. النموذج لا يتصل بقاعدة البيانات اتصالًا مباشرًا غير مقيد، ولا يتجاوز واجهات الخدمات المصرح بها.
- **خدمة AI مستقلة:** طبقة قابلة للاستبدال لتوجيه المهام إلى مزود/نموذج مناسب للصوت والنص والصور والتلخيص. تُرسل أقل كمية بيانات لازمة وبعد التحقق من الصلاحيات ومراجعة الخصوصية وموقع المعالجة.
- **n8n:** للأتمتة المجدولة، وتكاملات واتساب، وتنسيق الأحداث وإعادة المحاولة. ليس مصدر الحقيقة ولا صاحب قرار الصلاحيات أو الحسابات.
- **طابور مهام وعمال خلفيون:** للمهام الطويلة أو كثيفة الموارد؛ مع معرف فريد، وحالة تقدم، وحدود تزامن، ومهلات، وإعادة محاولة محسوبة، وطابور فشل. لا تُعلّق استجابة واجهة الطبيب على مهمة طويلة.
- **سجل AI ومراقبة التكلفة:** تسجيل نوع المهمة والعيادة والمستخدم والنموذج والمدة والحالة والتكلفة التقديرية ومراجع البيانات، مع حجب المحتوى الطبي غير اللازم والأسرار.
- **فصل الأولويات:** مساعد الطبيب أولًا، ثم المساعد الإداري، ثم مساعد الاستقبال. راجع `AI_ASSISTANTS_REQUIREMENTS.md` للتفاصيل واختبارات القبول.
- **التعطل الآمن:** عند توقف مزود AI أو n8n تبقى الوظائف اليدوية الأساسية متاحة، ولا تضيع المدخلات، ولا تتكرر العمليات الحساسة.
